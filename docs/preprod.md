# 准生产发布

基线：git tag `v0.31.0-beta.1`（插件 `@ziqu/plugin-dingze` 0.31.0 + 门户 `dingze`）。发布步骤沿用[发布与部署](deploy.md)，这里列准生产要多做的准备和检查。

## 0. 环境

| 环境 | 地址 | NocoBase | 现状 | 用途 |
|---|---|---|---|---|
| 开发 / 测试（dev） | https://ziqu-dev.aihupo.cn/x/dingze/ | 2.4.0-alpha.9 | 插件 0.31.0、门户、演示数据（原 `ziqu.aihupo.cn`，2026-10-16 改域名） | 日常迭代、甲方试用、演示 |
| 准生产 | https://ziqu.aihupo.cn/x/dingze/ | 2.4.0-alpha.11 | 新实例，还没有定责插件和门户（2026-10-16 核对） | 真实企业试运行 |

- 准生产比 dev 高两个小版本（alpha.11 / alpha.9）。插件是对着 alpha.9 构建和验证的，上准生产前要先在 alpha.11 上验证：用 alpha.11 源码重新构建插件、安装后跑一遍“发布后验证”。如果 dev 也计划升级到 alpha.11，建议先升 dev 验证再发准生产。
- 开发机的 `nb` 只配置了 `ziqu-dev` 一个环境；准生产的管理员凭据到位后再单独加 `ziqu-preprod`，发布命令显式指定环境，避免开发时误发到准生产。

## 1. 发布前要定下来的（需求方 / 运维）

| 事项 | 说明 | 谁定 |
|---|---|---|
| 准生产实例 | 新建一个 NocoBase 实例，还是在现有实例上新开应用？域名与 HTTPS 证书。版本要与测试环境一致（2.4.0-alpha.9），否则先在测试环境验证新版本 | 运维 |
| 数据口径 | 空库开始（只建真实企业），还是带演示数据。建议：准生产不放演示企业，演示继续用测试环境 | 需求方 |
| 大模型服务 | 准生产用哪个服务和模型，API 密钥由运维在实例的 AI 设置里配置（不经过代码仓库）；资料发往外部模型的告知口径（规格 Q8）要先确认 | 需求方 + 运维 |
| 邮件通知 | 是否开 `dingze-email` 通道（SMTP）。不开则只有站内通知 | 需求方 |
| 登录方式 | 只用账号密码，还是接钉钉等。接钉钉时“自动注册”要关闭（不开放公开注册） | 需求方 |
| 账号 | 运营管理员、咨询管理员、咨询师名单；首批企业与企业管理员 | 需求方 |
| 备份 | 数据库定时备份与保留期；发布前做一次全量备份 | 运维 |
| 部署形态 | 单实例还是多实例。多实例前要把邀请码注册的限流计数换成共享存储（现在是进程内） | 运维 |

## 2. 发布步骤

1. **备份**目标实例（数据库 + 上传文件）。
2. **插件**：用 tag 对应代码构建并安装 `@ziqu/plugin-dingze` 0.31.0（`deploy.md` 第 1 节）。首次启用会创建 5 个系统角色和 3 位数字咨询师（`dingze-strategy-coach`、`dingze-goal-coach`、`dingze-action-coach`）。
3. **大模型**：在实例的 AI 设置里配置大模型服务，确认 3 位数字咨询师可以对话。
4. **门户**：`nb portal create / config / deploy dingze`（`deploy.md` 第 2 节）。
5. **门户入口**：给 5 个定责角色开 `dingze` 入口（`deploy.md` 第 3 节），只影响本门户。
6. **初始账号**：建运营管理员、咨询管理员；初始密码单独安全转交，首次登录后修改。
7. （可选）建 `dingze-email` 通道。

## 3. 发布后验证

| 检查 | 方法 |
|---|---|
| 三类角色能进入 | 咨询师 → 咨询师工作台；企业项目负责人 → 我的项目；运营 → 运营管理（`deploy.md` 第 4 节） |
| 一张表走完流程 | 建一家测试企业和项目，S1-01 填写 → 本步完成 → 提交复核 → 复核通过 → 企业确认定版，导出 Excel / Word 正常 |
| 数字咨询师 | 在 S1-01 对话里点“这张表还缺什么”，有回复；修改卡确认后才写入 |
| 跨企业隔离 | 跑 `e2e/dingze-isolation.spec.ts`（`deploy.md` 第 6 节） |
| 通知 | 提交复核后主咨询师收到站内通知（开了邮件通道的同时收到邮件） |
| 清理 | 验证用的测试企业停用；临时账号重置或停用 |

## 4. 回滚

- 门户：重新部署上一个 tag 的代码（`git checkout <上一个 tag>` 后 `nb portal deploy dingze`）。
- 插件：安装上一个版本的插件包。插件的数据表只增不删，旧版本可以读新数据；如果新版本做过数据合并（`server/upgrade/`），回滚前先恢复备份。
- 数据：用发布前的备份恢复。

## 5. 发布后的版本规则

- 准生产每次发布都打 tag：`v<插件版本>-rc.<n>`；正式生产用 `v<插件版本>`。
- 只改门户的发布不升插件版本，tag 用 `v<插件版本>-rc.<n>` 的下一个序号。
- 每次发布在[更新记录](changelog.md)里写清楚改了什么、试用者要注意什么。
