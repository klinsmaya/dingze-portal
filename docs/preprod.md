# 准生产发布

基线：git tag `v0.31.0-beta.1`（插件 `@ziqu/plugin-dingze` 0.31.0 + 门户 `dingze`）。发布步骤沿用[发布与部署](deploy.md)，这里列准生产要多做的准备和检查。

## 0. 环境

| 环境 | 地址 | NocoBase | 现状（2026-10-16） | 用途 |
|---|---|---|---|---|
| 开发 / 测试（dev） | https://ziqu-dev.aihupo.cn/x/dingze/ | 2.4.0-alpha.11 | 插件 0.32.2、门户、演示数据（原 `ziqu.aihupo.cn`，当天改域名并升级到 alpha.11） | 日常迭代、甲方试用、演示 |
| 准生产 | https://ziqu.aihupo.cn/x/dingze/ | 2.4.0-alpha.11 | **已发布**：多空间插件、定责插件 0.32.2、门户、5 个角色入口、数字咨询师用 DeepSeek Flash、演示数据（从 dev 迁入） | 真实企业试运行 |

- 开发机的 `nb` 有两个环境：`ziqu-dev`（默认）和 `ziqu-preprod`。发准生产时命令一律显式带 `-e ziqu-preprod -y`，不改默认环境。
- `nb portal deploy` 会把目标环境的 API 地址写进本地 `.env.local`；发完准生产后要改回 dev 地址（`NOCOBASE_API_URL=https://ziqu-dev.aihupo.cn/api`），否则本地开发会连到准生产。

## 2. 发布步骤

1. **备份**目标实例（数据库 + 上传文件）。
2. **插件**：用 tag 对应代码构建并安装 `@ziqu/plugin-dingze` 0.31.0（`deploy.md` 第 1 节）。首次启用会创建 5 个系统角色和 3 位数字咨询师（`dingze-strategy-coach`、`dingze-goal-coach`、`dingze-action-coach`）。
3. **大模型**：在实例的 AI 设置里配置大模型服务，确认 3 位数字咨询师可以对话。
4. **门户**：`nb portal create / config / deploy dingze`（`deploy.md` 第 2 节）。
5. **门户入口**：给 5 个定责角色开 `dingze` 入口（`deploy.md` 第 3 节），只影响本门户。
6. **初始账号**：建运营管理员、咨询管理员；初始密码单独安全转交，首次登录后修改。
7. （可选）建 `dingze-email` 通道。

## 2.1 演示数据迁移（dev → 准生产）

准生产带演示数据（2026-10-16 确认）。只迁定责的数据，不整库还原（dev 上还有其他应用）：

- 范围：5 个企业空间（瀚川燃气、启衡能源、澜岳食品、北辰物流、远舟新材）、定责账号（运营、咨询方、企业成员，共 19 个）、各 `dz_*` 表（项目、成员、组织、各表与版本、流转与审计、批注、异议、导出记录、专家咨询、邀请码与申请、引导缺口、通知、画像、资料），资料原件（本次没有）。不迁：AI 对话记录、超级管理员、dev 上的其他应用。验证用的两个“功能测试”项目排除。
- 工具：插件里的 `dingze:exportSnapshot` / `dingze:importSnapshot`（只给超级管理员）。导入要求目标实例的定责表是空的；记录按原编号写入，写完把自增序号校正到最大编号之后；不在快照里的账号引用改指向目标实例的管理员。
- 步骤：
  1. 在 dev 上导出快照（只读）。
  2. 准生产装好插件后，先 `dryRun` 演练：整个事务回滚，只返回将写入的条数。
  3. 正式导入。演示账号用随机初始密码，写进运维本地文件，不经过聊天和文档；由运营重置后单独转交。
  4. 核对：各表条数与 dev 一致；用演示账号登录，打开瀚川 2026 的 S3-02、启衡 2027 的 S2-03 和资料页、运营看板。
- 2026-10-16 在 dev 上导出过一次：5 个空间、19 个账号、7 个项目、31 张表、98 个版本、427 条审计、659 条通知、11 份资料（都是文字，没有原件）。正式迁移前在 dev 定版后重新导出一次。

## 4. 回滚

- 门户：重新部署上一个 tag 的代码（`git checkout <上一个 tag>` 后 `nb portal deploy dingze`）。
- 插件：安装上一个版本的插件包。插件的数据表只增不删，旧版本可以读新数据；如果新版本做过数据合并（`server/upgrade/`），回滚前先恢复备份。
- 数据：用发布前的备份恢复。

## 5. 发布后的版本规则

分支、tag 和一次升级的完整步骤见[发布与部署](deploy.md)第 0 节。

- 准生产每次发布都打 tag：`v<插件版本>-rc.<n>`；正式生产用 `v<插件版本>`。
- 只改门户的发布不升插件版本，tag 用 `v<插件版本>-rc.<n>` 的下一个序号。
- 每次发布在[更新记录](changelog.md)里写清楚改了什么、试用者要注意什么。
